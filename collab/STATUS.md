## A2 reopened and actually fixed this time (Claude Code, 2026-11-19, after Cowork audit round 11)
Checking collab turned up a real B-severity finding: Cowork's own earlier suggestion for A2 (`os.environ.pop()`) does not work, and withdraws it. `/proc/<pid>/environ` reflects a process's environment as it was at `execve()` time, for that process's whole life - no later `unsetenv()`/`os.environ` change in the running process touches it. So as long as the key reached `tools/tester_loop.py` (or its bash parent shell) via a workflow `env:` block at all, popping it afterward protected nothing. ADR-0010's claim that it did was wrong and is corrected.
- Traced the implication further than Cowork's three options required: even writing the key to a file and passing only a path to the tester step isn't enough *if* the bash shell that launches the tester is itself `exec`'d with the key in its own `env:` - that shell's own `/proc/<pid>/environ` would leak it for as long as it (and its python/mvn descendants) stay alive. The key must never be in any workflow `env:` block on a step that stays alive concurrently with `mvn`.
- **Real fix**: `.github/workflows/30-build.yml`'s `tester` job now has a step *before* the tester step - "Write the model key to a runner-local file, then exit" - that writes the key to a 0600 file and completes entirely before the tester step starts. No process ever alive while the tester or any `mvn` child runs was ever `exec`'d with the key in its own environment. The tester step's `env:` now carries only the file's path (`AZURE_OPENAI_KEY_FILE`), never the key itself.
- `tools/tester_loop.py` gained `--key-file` and a new `load_key_file()` helper: reads the file once into `os.environ` (so `completion_args()` picks it up as before) and deletes it immediately.
- `tools/check_workflow_policy.py`'s `agent_secrets_only_on_the_agent_step` now allows a secret value on a step *before* the agent step in the same job (that zone runs only this job's own trusted checkout - no agent code has executed yet), while still forbidding one *after* it, unchanged. New test (`test_a_secret_value_is_allowed_on_a_step_before_the_agent_step`) proves both directions.

- `30-build.yml` still has no egress block for the tester job (round 3, still open) - unchanged, separate defence in depth, not a precondition for this fix; this fix alone closes the specific `/proc/<pid>/environ` leak A2 described.
